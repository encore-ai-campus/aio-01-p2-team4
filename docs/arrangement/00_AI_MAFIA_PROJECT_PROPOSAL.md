# AI 마피아 프로젝트 기획서

기획 기준: 프로젝트 착수 시점  
문서 성격: 구현 결과를 반영하기 전, 문제·사용자·서비스 목표·MVP 범위를 정의하는 기획 문서

## 1. 기획 배경

마피아 게임은 의심, 대화, 거짓말, 추리와 같은 사회적 상호작용을 핵심 재미로
삼는다. 그러나 여러 명의 참가자가 동시에 모여야 하므로 게임을 시작하기까지의
진입 장벽이 높다. 참여 인원이 부족하거나 게임 도중 탈락자가 발생하면 사용자는
게임을 충분히 즐기기 어렵다.

본 프로젝트는 이 문제를 AI 플레이어로 완화하고자 한다. AI가 단순한 대사를 반복하는
NPC가 아니라, 제한된 게임 정보와 공개 대화를 바탕으로 발언·행동·투표를 선택하는
플레이어가 되도록 설계한다.

## 2. 시장 및 경쟁 환경

제공된 시장 조사 자료는 마피아 게임을 보드게임·온라인 소셜 디덕션·스트리밍과
커뮤니티형 게임이 연결된 시장으로 바라본다. Among Us, Goose Goose Duck,
마피아42와 같은 사례는 소셜 디덕션의 반복 재미와 콘텐츠 확장 가능성을 보여준다.

동시에 이 시장은 상위 게임의 이용자 집중도와 네트워크 효과가 높아, 기존 마피아
규칙을 단순히 디지털화하는 전략만으로는 차별화하기 어렵다. 신규 서비스는 AI
플레이어, AI Game Master, 동적 사건, 짧은 플레이, UGC 등의 새로운 경험과 결합할
필요가 있다.

다만 제공된 시장 조사 자료의 시장 규모·동접·매출 수치는 본 프로젝트가 직접 검증한
자료가 아니므로 기획의 참고 근거로만 사용한다. 본 프로젝트는 외부 시장 수치를
성과로 주장하지 않고, 실제 구현과 시험 결과를 중심으로 가치를 검증한다.

## 3. 문제 정의

### 3.1 사용자 문제

- 함께 플레이할 사람을 모으기 어렵다.
- 참가자가 부족하면 게임을 시작할 수 없다.
- AI가 정해진 문장만 출력하면 추리와 대화의 재미가 약하다.
- AI가 다른 플레이어의 비공개 정보를 보거나 규칙을 임의로 바꾸면 공정성이 훼손된다.
- 역할과 규칙이 많아질수록 신규 사용자의 학습 부담이 커진다.

### 3.2 해결하고자 하는 핵심 문제

> 사람이 충분하지 않아도 사용자가 소셜 디덕션 게임을 시작하고 끝까지 진행할 수
> 있으며, AI의 행동은 자유롭되 정보·권한·규칙은 통제되는 게임 경험을 제공한다.

## 4. 목표 사용자

### 4.1 1차 사용자

- 마피아 게임을 좋아하지만 함께할 사람을 모으기 어려운 사용자
- 혼자서도 AI와 대화·추리 게임을 플레이하고 싶은 사용자
- 짧은 시간 동안 반복해서 다른 상황을 경험하고 싶은 사용자

### 4.2 2차 사용자

- AI 플레이어의 판단과 행동 과정을 관찰하려는 사용자
- Agent의 Tool 선택, 정보 격리, 오류 처리 구조를 평가하려는 개발자·관리자

## 5. 서비스 컨셉

### 5.1 한 줄 컨셉

**사람을 모으지 않아도 AI 플레이어들과 함께 완주하는 소셜 디덕션 게임**

### 5.2 서비스 설명

사용자는 게임을 생성하고 AI 플레이어들과 함께 역할을 배정받는다. 게임 중 AI는
자신에게 허용된 정보와 공개 대화를 바탕으로 발언, 밤 행동, 투표를 선택한다.
AI의 출력은 게임을 직접 변경하는 명령이 아니라 검증 대상인 proposal이며, 최종
규칙 적용과 승패 결정은 Backend Game Engine이 담당한다.

## 6. 제품 목표

### 6.1 사용자 목표

사용자가 별도의 참가자 모집 없이 게임을 생성하고, AI 플레이어들과 토론·행동·
투표를 거쳐 최종 결과까지 도달하도록 한다.

### 6.2 AI Agent 목표

AI가 다음의 판단 흐름을 수행하도록 한다.

```text
게임 Context 관찰
→ 현재 차례와 허용 행동 판단
→ 적절한 Tool 또는 행동 선택
→ 구조화된 proposal 생성
→ 결과·권한·규칙·상태 검증
→ 오류 수정·재시도·fallback 또는 안전 종료
```

### 6.3 품질 목표

- AI가 다른 플레이어의 비공개 정보를 사용하지 않는다.
- AI가 허용되지 않은 행동을 실행하지 못한다.
- 게임 규칙과 승패는 LLM이 아니라 게임 엔진이 결정한다.
- 오류가 발생해도 무한 반복이나 중복 상태 변경이 발생하지 않는다.
- Agent의 Tool 선택·호출·검증·fallback 흐름을 추적할 수 있다.

## 7. 핵심 사용자 시나리오

### 7.1 게임 생성

1. 사용자가 게임 시작을 요청한다.
2. 시스템이 게임 인원, 시나리오, 역할과 기본 설정을 준비한다.
3. 인간 플레이어와 AI 플레이어가 게임에 참여한다.
4. 사용자에게 현재 게임 상태와 진행 가능한 행동을 표시한다.

### 7.2 토론과 발언

1. 현재 토론 단계와 AI의 차례를 확인한다.
2. AI가 공개 정보, 자기 정보, persona와 이전 대화를 참고한다.
3. AI가 발언 또는 PASS를 선택한다.
4. 시스템이 차례·권한·상태 버전을 검증한 후 게임에 반영한다.

### 7.3 밤 행동과 투표

1. AI가 자신의 역할과 현재 허용된 행동을 확인한다.
2. 행동 또는 투표 대상을 선택한다.
3. 시스템이 phase, 대상, 권한, action window를 검증한다.
4. 모든 유효한 제출이 모이면 게임 엔진이 결과를 집계하고 다음 상태로 전환한다.

### 7.4 오류 상황

Tool 오류, 잘못된 파라미터, 오래된 상태, 인증 실패 또는 Provider 지연이 발생하면
시스템은 오류를 분류한다. 오류 유형에 따라 보완 질문, 제한된 재시도, 대체 행동,
deterministic fallback 또는 안전한 종료를 선택한다.

## 8. MVP 범위

### 8.1 포함할 기능

- 인간 사용자 한 명과 여러 AI 플레이어의 게임
- 6~9명 규모의 기본 게임 진행
- 역할·시나리오·phase·승패 처리
- 낮 토론, 밤 행동, 투표·재투표, 최종 지목
- AI 발언·PASS·밤 행동·투표 proposal
- actor별 Context와 비공개 정보 격리
- Backend Game Engine의 행동·권한·상태 검증
- MCP Resource·Prompt·Tool 연동 구조
- Provider·MCP 오류에 대한 retry와 fallback
- 저장·재개·관전·결과·feedback
- 게임 상태와 Agent activity 확인

### 8.2 MVP에서 제외할 기능

- 실제 이용자 간 대규모 매칭
- AI 플레이어 간 직접 협업·handoff
- AI가 규칙과 사건을 동적으로 생성하는 Game Master
- 사용자가 사건·직업·규칙을 만드는 UGC
- 수익화, 시즌패스, 랭킹과 운영형 커뮤니티
- 모델 내부 추론 전문의 저장·공개
- 자동 프롬프트 학습과 자기학습

위 항목은 장기 확장 후보이며, MVP의 성공 여부와 혼동하지 않는다.

## 9. 기능 요구사항

### 9.1 게임 기능

- 사용자는 게임을 생성하고 진행 상태를 조회할 수 있어야 한다.
- 사용자는 자신의 합법적인 행동을 제출할 수 있어야 한다.
- 게임 엔진은 phase, 차례, 생존 여부, 대상과 승패를 검증해야 한다.
- 사용자는 저장한 게임을 다시 이어서 진행할 수 있어야 한다.

### 9.2 Agent 기능

- Agent는 actor별로 허용된 Context만 읽어야 한다.
- Agent는 현재 action window의 허용 Tool만 선택해야 한다.
- Provider 출력은 구조화된 proposal로 변환·검증되어야 한다.
- 실패한 proposal은 정해진 정책에 따라 수정·재시도·fallback되어야 한다.
- 실행 결과에는 관찰 가능한 activity와 확정 event가 남아야 한다.

## 10. 비기능 요구사항

- 정보 격리: 다른 actor의 private role·fact·미공개 행동을 노출하지 않는다.
- 결정성: 게임 규칙·승패·최종 상태는 Backend 원장과 Game Engine이 결정한다.
- 멱등성: 동일 요청과 늦은 결과가 상태를 중복 변경하지 않는다.
- 복구성: worker·Provider·MCP 오류와 재시작 상황을 안전하게 처리한다.
- 관찰성: Agent의 주요 실행 단계와 실패 원인을 확인할 수 있다.
- 재현성: Fake·Dummy Provider로 핵심 Agent 흐름을 반복 시험할 수 있다.

## 11. 성공 기준

### 11.1 사용자 경험 기준

- 참가자 모집 없이 사용자가 게임을 시작할 수 있다.
- 인간과 AI가 함께 게임을 최종 결과까지 진행할 수 있다.
- 저장·재개와 새로고침 후에도 게임 상태가 유지된다.
- 사용자가 AI의 진행 상태와 최종 결과를 이해할 수 있다.

### 11.2 Agent 평가 기준

동일한 시험 데이터에 대해 검증·성찰 루프 적용 전후를 비교한다.

- 태스크 완료율
- Tool·행동 선택 정확도
- Backend 검증 통과율
- 응답과 실제 결과의 일관성
- 정보 격리 성공률
- fallback 성공률
- 평균 재시도 횟수
- 평균 처리 시간

각 지표는 시험 입력, 기대 결과, 판정 기준과 원본 실행 로그를 근거로 산출한다.

## 12. 예상 시스템 방향

기획 단계의 목표 구조는 다음과 같다.

```text
User Frontend
→ Backend API
→ Game Service / Game Engine
→ Agent Orchestrator
→ Context·Provider·MCP Tool
→ 검증된 Action Proposal
→ Game Engine 최종 반영
→ Event·Receipt·Activity
→ Frontend 상태 표시
```

핵심 경계는 다음과 같다.

- Agent와 LLM은 게임 DB를 직접 변경하지 않는다.
- MCP Server는 PostgreSQL·Redis에 직접 접근하지 않고 Backend 내부 API를 호출한다.
- 모델 출력은 확정 명령이 아니라 검증 전 proposal이다.
- 모델의 내부 추론 전문은 저장·공개하지 않고 실행 이벤트만 기록한다.

세부 구조는 [전체 시스템 아키텍처 설계서](AI_MAFIA_SYSTEM_ARCHITECTURE_DESIGN.md),
데이터·API·MCP·화면 계약은 각 하위 설계서를 따른다.

## 13. 기대 효과

### 단기 효과

- 참가자 부족으로 시작하지 못하는 문제 완화
- AI와 대화·추리하는 새로운 게임 경험 제공
- AI Agent의 Tool 사용과 검증 흐름을 확인할 수 있는 MVP 확보

### 장기 가능성

- AI persona와 역할 확장
- 짧은 플레이 모드
- AI Game Master와 동적 사건
- 친구 초대 및 실시간 멀티플레이
- 사용자 제작 시나리오

장기 가능성은 후속 제품 가설이며, 본 MVP에서 구현되었다고 전제하지 않는다.

## 14. 주요 위험과 대응 방향

| 위험 | 대응 방향 |
|---|---|
| AI가 잘못된 행동을 선택함 | 구조화 출력과 Backend·Game Engine 이중 검증 |
| 비공개 정보가 섞임 | actor별 Context projection과 scope 검증 |
| Provider·MCP 지연 | timeout, 제한 재시도, fallback |
| 신규 사용자가 규칙을 어려워함 | MVP 역할·시나리오를 제한하고 단계적으로 안내 |
| AI 발언 품질이 낮음 | 대표 대화 데이터셋과 persona별 평가·개선 |
| 시장 경쟁이 강함 | 기존 게임 복제가 아닌 AI 기반 최소 인원 해결에 집중 |
