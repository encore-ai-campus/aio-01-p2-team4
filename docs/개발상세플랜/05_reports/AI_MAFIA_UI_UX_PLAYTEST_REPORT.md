## 1. 목적과 판정 기준

Orca 내장 브라우저에서 새 6인 게임 한 판을 생성해 역할 공개부터 결과 화면까지
실제로 진행하고, 처음 플레이하는 사용자가 게임 상태와 자신의 다음 행동을 이해하고
제때 조작할 수 있는지 확인했다. 브라우저 관찰과 별도로 화면 정본과 현재
`frontend_user` 구현을 읽기 전용으로 대조했다.

우선순위는 다음과 같이 사용한다.

| 우선순위 | 의미 |
|---|---|
| P0 | 진행 불가, 잘못된 판정 또는 비공개 정보 노출 |
| P1 | 핵심 플레이, 복구 또는 사용자의 의사결정을 크게 훼손 |
| P2 | 중요한 정보·조작성·접근성의 누락 |
| P3 | 일관성, 완성도 또는 후속 검증이 필요한 문제 |

실게임에서 P0 문제는 발견하지 않았다. 생성·진행·저장·재개·승패 확정과 결과 조회는
서버 오류 없이 완료됐다. 가장 큰 문제는 인간이 선택해야 하는 행동이 긴 화면 아래에
묻히고 새 차례 알림이 약해, 탐정 조사와 낮 투표가 모두 자동 선택으로 끝난 점이다.

## 2. 실행 환경과 한 판 결과

| 항목 | 값 |
|---|---|
| 실행 시각 | 2026-09-07 12:56~13:03 KST |
| 브라우저 | Orca 내장 브라우저, Chromium 150 계열 |
| viewport | 1108 × 1019 CSS px |
| 사용자 Frontend | `http://127.0.0.1:18501` |
| Backend | `http://127.0.0.1:18000` |
| 의존성 | 격리 PostgreSQL·Redis ready, dummy Provider |
| 게임 | 6인, `호텔 만찬의 마지막 손님` |
| 인간 역할 | 플레이어 1 · 탐정 |
| 결과 | 시민 진영 승리, 플레이어 4 마피아 처형 |
| 추가 확인 | 저장·홈 복귀·재개, 결과의 전체 역할·밤·투표·발언 기록 |

게임 시작 뒤 인간은 낮 1일차와 낮 2일차에 두 번 발언했다. 첫날 밤에는 플레이어 2
의사가 사망했고, 낮 2일차 투표에서 플레이어 4 마피아가 처형됐다. 인간의 탐정 조사와
낮 투표는 직접 선택하지 못하고 플레이어 5로 자동 선택됐다. 조사 결과는
`마피아가 아닙니다`로 다음 낮에 보존됐고, 최종 결과에는 자동 선택 여부까지 기록됐다.

브라우저 콘솔 오류는 없었다. 관찰한 SSE 연결과 정적 자원 요청은 HTTP 200이었고,
저장 후 발언·생존자·조사 결과·공개 타임라인이 같은 상태로 복원됐다. 테스트 도중
Orca의 장시간 `wait` 한 번이 runtime 연결 오류를 반환했지만 제품은 계속 진행됐고
즉시 재접속됐다. 이 오류는 제품 결함에서 제외한다.

## 3. 잘 된 점

- 홈의 게임 시작 CTA와 예상 인원·시간이 눈에 잘 띄었고, 빈 게임 목록 안내도
  다음 행동을 분명히 제시했다.
- 역할 공개 화면은 역할, 승리 조건, 사건, 알리바이와 관찰 정보를 한 흐름으로 보여
  게임 맥락과 비공개 정보 경계를 이해하기 쉬웠다.
- 인간 발언을 제출한 뒤 성공과 다음 AI 차례가 표시됐고, AI별
  `대기 → 판단 중 → 적용 완료` 상태는 장시간 대기의 원인을 이해하는 데 도움이 됐다.
- 저장·재개는 기능적으로 안정적이었다. 홈 카드, 게임 내부 재개, 조사 결과와
  타임라인이 일관되게 복구됐다.
- 결과 화면은 승리 진영, 종료 이유, 전체 역할, 밤 기록, 투표 집계와 개별 선택,
  공개 발언을 서버 확정 정보로 분리해 회고 가능성이 높았다.
- 역할과 생존 상태를 색상뿐 아니라 텍스트로 함께 표시했고, 주요 CTA와 입력에는
  접근성 이름이 있었다.

테스트 자동화 호환 문제일 수 있다. 실제 마우스·터치로 재현되기 전에는 제품 결함으로
확정하지 않는다.

## 6. 권장 적용 순서

저장소 규칙에 따라 한 구현 세션은 마스터플랜 작업 단위 하나 이하로 나눠야 한다.
다음 순서는 우선순위이며 한 번에 모두 구현하라는 뜻이 아니다.

1. **WU-F4:** UX-01·02·13·15·16을 묶어 행동 가시성, countdown, 투표 근거와
   최종 지목 설명을 먼저 고친다.
2. **WU-F3/WU-F5:** 공통 게임 shell의 내비게이션, 실제 연결 상태, STALE 잠금과
   phase별 timeline을 정리한다.
3. **WU-F2:** 인원 선택 상태, 역할 preview와 시간 규칙, 홈 카드 메타데이터를 보완한다.
4. **WU-F6:** 관전 phase와 결과 CTA·metric 반응형·기록 기본 접힘을 개선한다.
5. **WU-F7:** 피드백 초기 별점과 재진입 상태를 고친다.
6. 각 WU 뒤 375×812 모바일, 1108px 데스크톱, 키보드 전용과 스크린리더로
   해당 흐름만 집중 검증한다.

### 6.1 WU-F4 적용 상태

2026-09-07 후속 작업에서 `UX-01·02·13·15·16`을 `WU-F4` 범위로 적용했다.

- 생존자의 현재 행동 패널을 phase 제목 바로 아래로 옮기고, 새 인간 행동 window에서
  한 번만 행동 영역과 첫 입력으로 이동·focus한다.
- 현재 할 일과 남은 시간을 데스크톱·모바일 하단 고정 요약으로 유지하고, 밤 10초와
  투표 15초·5초 경고를 임계값 단위 `aria-live=polite`로 제공한다.
- 모든 진행 phase의 중앙 공개 타임라인을 유지한다.
- `VOTE_RESOLVED`의 후보별 득표수와 동률·재투표 여부를 공개 이름으로 표시하고,
  계약 밖 필드·알 수 없는 참가자·모순된 집계는 원문을 노출하지 않고 거부한다.
- 최종 지목에는 마피아·시민 선택의 즉시 승패와 동률 시 재투표 없이 서버가
  결정적으로 한 명을 선택한다는 규칙을 고정 안내한다.
- 집중 테스트 219개와 프런트 전체 회귀 테스트 363개를 통과했다. Python compile과
  행동 보조 JavaScript 구문 검사도 통과했다.
- 재시작한 로컬 서버의 9인 진행 게임으로 데스크톱과 375×812 viewport를 확인했다.
  행동 패널이 phase 직후에 나오고, 하단 현재 행동 요약과 공개 타임라인이 유지되며,
  새 행동에서 `발언 내용` 입력에 한 번만 focus되는 것을 확인했다.

### 6.2 WU-F3 공통 이동 적용 상태

2026-09-07 후속 작업에서 `UX-03`의 홈 이동 문제를 `WU-F3` 범위로 일부 적용했다.

- 홈을 제외한 모든 사용자 화면에 실제 `뒤로가기`와 `홈` button을 공통으로 표시한다.
- 뒤로가기는 검증된 앱 내부 방문 기록을 사용하고 기록이 없으면 홈으로 이동한다.
- 홈 이동은 진행 게임·작성 중 입력·결과 불명 요청을 보존하며, 최신 목록을 위해 홈
  cache만 무효화한다.
- 두 이동 button은 375×812 viewport에서도 숨기지 않는다.
- 공통 이동 집중 테스트 8개와 프런트 전체 회귀 테스트 371개를 통과했다. 실제
  브라우저에서 홈→새 게임→뒤로가기, 홈→진행 게임→홈, 홈→피드백→뒤로가기 흐름과
  모바일 표시를 확인했다.

`UX-03`의 wordmark·피드백·설정 제어와 나머지 `UX-04~12·14·17~26`은 각각의 권장
WU 범위에 남아 있다.

## 7. 이번 검증의 한계

- 6인·인간 탐정·dummy Provider 한 판의 관찰이므로 모든 역할, 8~9인 레이아웃,
  재투표·최종 지목·관전 흐름을 실게임으로 모두 확인하지 않았다.
- 실제 모바일 기기·모바일 emulator, VoiceOver/NVDA와 200% 확대는 실행하지 않았다.
- 포인터 click 무반응은 자동화 환경 한정 가능성이 있어 제품 결함으로 확정하지 않았다.
- 외부 Cloud API나 유료 Provider를 사용하지 않았다.
- 이번 적용은 Front `WU-F4`에 한정했으므로 Backend·MCP 전체 회귀 테스트는 실행하지
  않았다. Backend `/health`·`/ready`, Frontend health와 실제 게임 화면은 직접 확인했다.
